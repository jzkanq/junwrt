# AW1000 NSA throughput investigation — 2026-10-15

The tester reports about 300 Mbps on SHADY and 50–70 Mbps on JunWRT, with NSA B28+n78. They installed the JunWRT sysupgrade `.bin` with `sysupg`. These are reported rates; no same-device capture or live router access was available for this investigation.

The identified SHADY `.bin` is byte-identical to the vendor baseline (SHA-256 `cda3729452682b3de5b22026dd27e77a4cf2782ec04d76acded9a483a6df1675`). The September JunWRT image used the same boot, modem, DSP, MCF and signature members. The firmware differences are in its rootfs. This excludes a changed packaged baseband as the explanation, but does not exclude modem settings saved outside rootfs.

## Findings and changes

1. **RF-path regression:** the old `WinSCP_Deploy_Modem/junspeedpatch.sh` called `arc_antenna_switch stop` and `disable`. The legitimate `/sbin/arc-antenna-switch.sh` reads board revision and the antenna selector, then controls GPIO 19 and 11 to select internal or external antennas. Disabling its init service removes that selection at subsequent boots. The rebuilt firmware keeps the sanitized service enabled and supervises the RF and USB helpers with procd. Its vendor downloader and timed-reboot logic remain removed. This is the strongest identified RF regression; whether it caused the tester's n78 loss remains unverified. No particular GPIO level is forced, and the supported-board guard remains in place.

   This was also verified in the preserved September firmware tar itself: `etc/init.d/junspeedpatch` lines 112–113 call the RF service's `stop` and `disable`. The new package's `OLD_FIRMWARE_RF_EVIDENCE.txt` records the input, member hash and line evidence; this is not merely a defect found in a later working-tree source.
2. **Late interfaces missed steering:** the old service wrote RPS/XPS only to queues present during startup. `96-junspeedpatch` now applies the same settings to validated interfaces on `ifup`/`ifupdate`, including recreated cellular queues. It resolves the actual L3 device when hotplug has no DEVICE. It never reloads the firewall, restarts the radio or writes UCI. RPS is software receive processing, not IRQ affinity; configured masks alone do not prove a speed improvement. [Linux networking scaling documentation](https://docs.kernel.org/networking/scaling.html).
3. **Actual Wi-Fi permission bug:** the firmware builder preserved unchanged vendor init files at 0664. It now stores them as 0755, including `wifi_state`; the current controller saves enable/disable state. This repairs persistence, not NSA carrier aggregation.
4. **Outdated firmware sources:** the builder's hand-picked flat WinSCP files could override newer canonical assets (the cockpit copies differed). Canonical `stock_rootfs` installer assets now win except for the generated banner and explicit firmware MSS rules. The new image contains the current five feature modules, Speed Test, Parental Control, Wi-Fi/controller fixes, Ad Blocker and current WebUI assets.
5. **Deployment divergence:** the legacy master installer embedded a different speed service that enabled generic offload=1. The tester used a `.bin`, so this is not their established trigger. Its embedded service is now synchronized to the same offload-disabled source as firmware and the current WebUI installer. Shared MSS rules survive a steering stop. The unsupported PREROUTING path-MTU clamp was removed; Linux permits that operation in FORWARD/OUTPUT/POSTROUTING. [Kernel TCPMSS implementation](https://code.googlesource.com/linux/torvalds/linux/+/9206b22fb959f4a9cf1921f34aed0df1dcb1ab04/net/netfilter/xt_TCPMSS.c).
6. **Build identity:** the firmware writes a Support build stamp with `source=firmware` and a manifest of its actual built assets. JunWRT UCI templates and device calibration files are not shipped. CPU governors remain dynamic; no speculative band, SA/NSA, RF, frequency or acceleration setting was forced.

## New artifacts and static verification

The isolated package is `output/JunWRT_AW1000_Firmware_20261015/`; its scratch tar/rootfs is under `build/`. The September image, earlier comparison tars and vendor/SHADY inputs are preserved. The current WebUI installer is regenerated in the workspace, WinSCP, Git deploy and existing release deployment locations. Nothing was flashed, deployed or pushed.

The audits accept `JUNWRT_OUTPUT_DIR`, and the builder additionally accepts `JUNWRT_BUILD_DIR`. Both gates verify actual firmware permissions, performance/copy/installer parity, preserved RF supervision, reconnect hooks, current modules and the Support manifest. A failure or warning produces a nonzero exit. Passing static checks does not certify bootloader acceptance or cellular throughput.

Validation results and SHA-256 values are recorded in `output/JunWRT_AW1000_Firmware_20261015/VALIDATION.md` after the checks finish. The performance regression exercises actual service/hotplug logic with fake sysfs/tools; it covers startup, late creation, reconnection, L3 fallback, invalid device names, disabled service, stop/MSS preservation and supported/unsupported board supervision. It does not exercise real GPIO or radio negotiation.

## Live acceptance needed to identify the remaining cause

Use the same router, SIM, location, antenna position, server, protocol, client and time window. Record whether the previous flash retained settings. Do not compare a phone or a different carrier/server as if it were a firmware-controlled result.

1. Run a sustained download while the Modem cockpit is open. Capture the primary B28 and secondary n78 cell, PCI, bandwidth, RSRP/RSRQ/SINR and RX0–RX3 readings **during traffic**. An idle 5G badge or n78 listing does not establish an active NR data leg. Export **Modem → Support** diagnostics while the transfer is running; the bundle now contains `performance.txt` with cached raw modem CA/cell/signal data, queue masks, CPU/interrupt statistics, thermal readings, Ethernet link information and qdisc statistics. Read-only CLI alternative: `/etc/init.d/junspeedpatch status`.
2. Compare router-side **Modem → Speed Test** with the client test (a router test may use about 260 MB). If the router test is fast while the client test is slow, inspect the LAN/Ethernet/Wi-Fi or forwarding/proxy path. Record the server/protocol; different servers can produce different rates.
3. If n78 is absent during traffic, compare RF selection and all four antenna readings, actual SA/NSA option state, stored band/cell locks and APN/AMBR. Do not reset NVRAM, copy another unit's calibration or force undocumented AT commands as a shortcut.
4. If n78 remains active with comparable signal/bandwidth but throughput stays low, inspect CPU load/frequency and thermal limits during transfer, softnet drops, qdisc shaping, Ethernet negotiation and the forwarding/proxy/VPN path. A loaded `mtk_warp` module is not proof that the transfer is accelerated. Capture before/after reconnect as well as after a full reboot.
5. Accept the throughput repair only when comparable JunWRT runs recover the vendor result and still do so after reboot/reconnect, with no new latency, upload, VPN or Wi-Fi persistence regression.

The rebuilt image retains the vendor `root_ro.sig` beside a modified rootfs. Bootloader acceptance remains unproven by these static checks. The project's LK/recovery preconditions in AGENTS.md still apply before flashing; building this artifact does not waive them.
